# תוכנית ביצוע: תהליך חתימה פר-לקוח מול WeSign API

מסמך זה הוא תוכנית הביצוע הקונקרטית לתהליך שליחת מסמך
לחתימה של לקוח בודד, מבוססת על מפרט WeSign API 4.0.0.

הוא ממשיך את `docs/wesign-integration-plan.md` (הארכיטקטורה הכללית),
ומתמקד רק בזרימה של: יצירת מסמך, שליחה ללקוח, מעקב וקבלת המסמך החתום.

**הנחות יסוד** (מאושרות בשיחה):

- החתימה היא **פר-לקוח**: כל לקוח חותם בעצמו על המסמך שלו.
- החיבור ל-WeSign מתבצע דרך **חשבון שירות אחד** בצד השרת —
  הלקוח עצמו אינו מחזיק חשבון או token ב-WeSign.
- אין קוד קיים להחליף (ה-automation הקודם ב-Playwright
  אינו רלוונטי יותר) — זהו מימוש חדש מאפס.

---

## 0. מה עדיין חסר לפני שאפשר להריץ בפועל

לפני מימוש בפועל צריך משלושת אלה:

1. Credentials לסביבת test/sandbox:
   `WESIGN_API_BASE_URL`, `WESIGN_USERNAME`, `WESIGN_PASSWORD`.
2. Template ID קיים במערכת WeSign עבור המסמך שנשלח ללקוח
   (למשל: הצהרת נבחן / תעודת סיום / הסכם).
3. אישור: מה בדיוק פרטי הזיהוי של הלקוח שדרכם שולחים אליו
   את הבקשה לחתימה — טלפון (SMS/WhatsApp) ו/או אימייל.

התוכנית הזו כתובה כך שהיא ניתנת למימוש מיד כשהפרטים האלה יגיעו,
בלי לשנות מבנה.

## 1. זרימת התהליך המלאה (שלב-אחר-שלב)

```
[exam-simulator]                          [WeSign API]
      |                                          |
      |--- 1. POST /v3/Users/login ------------->|   (חשבון שירות, פעם אחת/ברענון)
      |<---------- token/refreshToken/authToken -|
      |                                          |
      |--- 2. GET /v3/Configuration ------------>|   (maxTemplatesPerProcess, בזמן ריצה)
      |<----------------------------------------  |
      |                                          |
      |--- 3. POST /v3/DocumentCollections ----->|   (יצירת מסמך מתבנית, נמען = הלקוח)
      |<------------------- documentCollectionId-|
      |                                          |
      |--- 4. POST /v3/Distribution ------------>|   (שליחה בפועל ללקוח: SMS/Email/WhatsApp)
      |<-------------------------- distributionId-|
      |                                          |
      |         (הלקוח מקבל הודעה, נכנס לקישור,   |
      |          חותם בצד WeSign)                |
      |                                          |
      |--- 5a. GET .../info/{id}  (polling) ---->|   או
      |--- 5b. Webhook callback <---------------  |   קבלת עדכון "סיום"
      |                                          |
      |--- 6. הורדת המסמך החתום ---------------->|
      |<--------------------------- קובץ חתום ---|
```

## 2. שלב 1 — אימות (Login)

**Endpoint**: `POST /v3/Users/login`

- מתבצע פעם אחת ונשמר בזיכרון/cache בצד השרת (לא per-request).
- יש לשמור את שלושת השדות מהתשובה: `token`, `refreshToken`, `authToken`.
- טיפול בתפוגה: אם קריאה מחזירה 401 — לרענן טוקן
  (או להתחבר מחדש) ולנסות שוב פעם אחת בלבד (לא ללולאה אינסופית).

קובץ מוצע: `lib/wesign/auth.ts`

```ts
export async function getValidToken(): Promise<string> {
  // 1. אם יש token בזיכרון ולא פג — להחזיר אותו
  // 2. אחרת — POST /v3/Users/login ולשמור את שלושת הטוקנים
  // 3. להחזיר token
}
```

**נקודת זהירות מהמפרט (סעיף 2.3)**: אם בעתיד יתווסף flow
של שינוי סיסמה לחשבון השירות (`POST /v3/Users/change`) —
הוא מפסיל את הטוקן הישן מיד ומחזיר שלושה טוקנים חדשים בגוף
התשובה. יש לעדכן את שלושתם יחד, לא רק את ה-token הראשי.

## 3. שלב 2 — קריאת קונפיגורציה (פעם אחת, cache-בזמן-ריצה)

**Endpoint**: `GET /v3/Configuration`

- לקרוא את `maxTemplatesPerProcess` ולשמור ב-cache
  (למשל TTL של שעה) — **לא לקודד 10 בקוד**.
- אם בעתיד תישלח יותר מתבנית אחת למסמך בודד —
  יש לוודא בקוד שהמספר לא חורג מהערך הזה לפני השליחה,
  כדי למנוע 400 מיותר.

עבור התהליך הבסיסי (מסמך אחד מתבנית אחת ללקוח)
הבדיקה הזו טריוויאלית (1 ≤ N), אך יש לקרוא את ה-endpoint
בכל זאת כחלק מ-health check/warm-up, כדי לתפוס בעיות
config מוקדם.

## 4. שלב 3 — יצירת המסמך ללקוח הספציפי

**Endpoint**: `POST /v3/DocumentCollections`

גוף הבקשה (לפי מה שנחשף במפרט, שדות עיקריים):

```json
{
  "templateId": "<TEMPLATE_ID>",
  "dateFormat": 1,
  "signers": [
    {
      "signerMeans": "<phone-or-email-of-customer>",
      "signerSecondaryMeans": "<optional second channel>",
      "emailNote": "הודעה אישית ללקוח (עד 250 תווים)"
    }
  ]
}
```

נקודות חובה מהמפרט שיש לממש כאן:

- **`dateFormat`** — שדה חדש בגרסה 4.0.0, ברירת מחדל 1 (Israeli).
  לשלוח תמיד במפורש, לא להסתמך על ברירת המחדל בשקט.
- **מגבלת תבניות** — לבדוק מול הערך שנשמר משלב 2
  לפני השליחה (ראו סעיף 2.4 במסמך השינויים).
- התשובה מחזירה מזהה (`documentCollectionId`) —
  **לשמור אותו מיד** במסד הנתונים הפנימי, ממופה לרשומת הלקוח
  (exam/candidate id ↔ documentCollectionId), עוד לפני השלב הבא —
  כדי לא לאבד את הקישור אם קריאת ה-Distribution תיכשל.

## 5. שלב 4 — שליחת המסמך בפועל ללקוח (Distribution)

**Endpoint**: `POST /v3/Distribution` (או `POST /v3/Distribution/signers`
אם מוסיפים נמענים לתהליך קיים)

```json
{
  "documentCollectionId": "<מהשלב הקודם>",
  "signers": [
    {
      "signerMeans": "<phone-or-email>",
      "sendingMethod": 2
    }
  ]
}
```

חוקי ולידציה חובה לממש בצד הלקוח **לפני** השליחה ל-API,
כדי לא לבזבז round-trip על 400 צפוי (סעיף 2.5 במסמך השינויים):

| `sendingMethod` | דרוש בנתוני הנמען |
|---|---|
| 1 (SMS) | טלפון תקין |
| 2 (Email) | אימייל תקין ב-`signerMeans`/`signerSecondaryMeans` |
| 4 (WhatsApp) | טלפון תקין, וזמינות ברמת החברה |

אם לא שולחים `sendingMethod` כלל — WeSign גוזר אותו לבד
מהנתונים (ברירת מחדל: אימייל תקין → Email, אחרת SMS).
**המלצה להתחלה**: לא לשלוח את השדה בכלל, ולתת ל-WeSign
לגזור — פחות מקרי קצה לטפל בהם בשלב ראשון.

התשובה מחזירה `distributionId` — לשמור גם אותו,
ממופה לאותה רשומת לקוח.

## 6. שלב 5 — מעקב אחרי סטטוס החתימה

שתי אפשרויות, לא סותרות (מומלץ לממש את שתיהן):

### 6.1 Polling (בסיסי, קל למימוש ראשוני)

**Endpoint**: `GET /v3/DocumentCollections/info/{id}`

- להריץ כל כמה דקות (למשל cron/interval) על כל מסמך
  שעדיין לא הגיע לסטטוס סופי.
- לשים לב לשדה `timeSent` בכל חותם: בגרסה 4.0.0 המשמעות
  היא זמן השליחה **הראשונה**, ויכול להיות `null` —
  הקוד חייב לטפל ב-null ולא להניח שדה מאוכלס תמיד.

### 6.2 Webhook / Call back (מומלץ לטווח בינוני)

- לפי ה-Release Notes: callback חוזר רק בסטטוס **"סיום"**
  (לא ב-"שמירה"), כך שה-endpoint שנבנה בצד שלנו יכול
  להניח שכל קריאה שמגיעה = תהליך הסתיים (נחתם/נדחה/בוטל).
- Endpoint מוצע: `POST /app/api/wesign/webhook`
- יש לוודא מול WeSign (סעיף 7 במסמך המקור,
  `pro-support@comda.co.il`) איך רושמים callback URL
  ברמת החברה/ברמת הבקשה, ואם יש מנגנון אימות/חתימה לבקשה
  הנכנסת — לפני שסומכים על הגוף שמגיע.

**המלצה לביצוע**: להתחיל עם polling בלבד (שלב 1),
ולהוסיף webhook כשיפור בשלב 2 — כי polling לא תלוי
בתשתית נוספת (כתובת ציבורית, אימות webhook) ומספיק
כדי לצאת ל-sandbox ולבדוק את כל שרשרת ה-happy-path.

## 7. שלב 6 — קבלת המסמך החתום

לאחר שסטטוס המסמך הגיע ל"הושלם"/"נחתם":

- להוריד את המסמך החתום (endpoint ההורדה — יש לאמת מול
  מפרט ה-OpenAPI המדויק של 4.0.0, לא מנוחש מהמסמך התמציתי).
- לשמור את הקובץ במקום קבוע (storage פנימי), ולקשר אותו
  לרשומת הלקוח.
- **הערה חשובה**: הורדה אפשרית רק למסמכים שנחתמו בפועל
  (לפי ה-Release Notes של הממשק החדש) — לבדוק סטטוס
  לפני ניסיון הורדה, לא להסתמך על try/catch בלבד.

## 8. טיפול בשגיאות בתהליך הזה ספציפית

| שלב | שגיאה צפויה | טיפול |
|---|---|---|
| Login | 401 | להתחבר מחדש פעם אחת; אם נכשל שוב — לדווח לניטור, לא לנסות בלולאה |
| DocumentCollections | 400 (חריגה ממגבלת תבניות) | לא רלוונטי לתהליך פר-מסמך-בודד, אך לבדוק מראש כהגנה |
| Distribution | 400 (sendingMethod לא תואם) | ולידציה מקומית לפני השליחה (סעיף 5 לעיל) |
| כל שלב עם קובץ | 413 (`ResultCode 163`) | לטפל כמו 400, להציג הודעה ברורה ללקוח שהקובץ גדול מדי |
| Polling | timeSent = null | להציג "טרם נשלח/טרם נצפה", לא לקרוס |
| Distribution/info | 401 באמצע polling ארוך | token עלול לפוג — לרענן ולנסות שוב פעם אחת |

כל שגיאה שמגיעה מ-WeSign (`ResultCode`) יש למפות דרך
`lib/wesign/errors.ts` (כבר מתוכנן במסמך הארכיטקטורה הכללי)
להודעה ברורה בעברית ללקוח/לצוות התמיכה, ולא להציג JSON גולמי.

## 9. מבנה נתונים פנימי נדרש (DB)

כדי לתמוך בתהליך פר-לקוח, נדרשת טבלה/רשומה פנימית לפחות עם:

```
customer_id            (המזהה הפנימי שלנו ללקוח/נבחן)
wesign_document_id     (documentCollectionId)
wesign_distribution_id (distributionId)
status                 (pending / sent / signed / declined / failed)
sent_at
signed_at
signed_file_url         (אחרי הורדה)
```

זה מה שמאפשר גם ל-polling וגם ל-webhook לדעת "איזה לקוח שייך
לאיזו חתימה" — בלי המיפוי הזה אי אפשר לסגור את הלולאה.

## 10. סדר מימוש מוצע (מצומצם, לפי התלות בפועל)

1. `lib/wesign/client.ts` + `auth.ts` — login + fetch wrapper.
2. `lib/wesign/types.ts` — טיפוסים ל-DocumentCollections/Distribution
   (טיפוסים "פתוחים", ראו סעיף 5.10 במסמך הארכיטקטורה הכללי).
3. Route: יצירת מסמך + שליחה ללקוח אחד (שלבים 3+4 לעיל) —
   happy path בלבד, ללא polling עדיין.
4. בדיקה ידנית מול sandbox: שליחה אמיתית ללקוח בדיקה,
   וידוא שההודעה מגיעה ושהקישור עובד.
5. Polling endpoint/cron לבדיקת סטטוס (שלב 6.1).
6. טבלת מעקב פנימית (סעיף 9) + חיבור ה-polling אליה.
7. טיפול בשגיאות מלא (סעיף 8) + מיפוי `ResultCode`.
8. הורדת מסמך חתום ואחסונו (שלב 7).
9. (אופציונלי, שלב הבא) Webhook במקום/בנוסף ל-polling.

## 11. מה עדיין דורש תשובה לפני שלב 4 בפועל (הרצה מול sandbox)

- כתובת ה-host וה-credentials לסביבת test.
- Template ID של המסמך שהלקוח חותם עליו.
- ערוץ שליחה מועדף כברירת מחדל — Email? SMS? להשאיר את WeSign
  לגזור אוטומטית (מומלץ, ראו סעיף 5)?
